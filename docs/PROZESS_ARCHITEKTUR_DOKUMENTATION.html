Die 2 Release-Pfade: Web-Publishing vs. Android App Bau

Je nachdem, ob Änderungen an der Webseite oder eine neue Version der Android-App veröffentlicht werden, greifen zwei unterschiedliche Wege:

Pfad A: Automatisches Web-Publishing (Webseite & PWA) Antigravity -> GitHub -> Hostinger

1. Änderung in Antigravity mit KI programmieren und testen.
2. npm run build ausführen (erzeugt das optimierte dist/ Bundle).
3. Im Terminal: git add ., git commit -m "feat: ..." und git push origin main.
4. Automatisch: GitHub informiert Hostinger per Webhook, Hostinger zieht den neuesten Stand in public_html.
5. Ergebnis: Die Webseite ist innerhalb von 30 Sekunden weltweit aktualisiert!

Pfad B: Android-App Bau & Google Play Release Capacitor -> Android Studio -> Google Play

1. Web-Build erstellen: npm run build im Projektverzeichnis ausführen.
2. Android-Synchronisation: npx cap sync android (kopiert dist/ in das native Android-Projekt).
3. In Android Studio öffnen: npx cap open android (oder Android Studio starten und Ordner android öffnen).
4. Signiertes Bundle bauen: Im Menü auf Build > Generate Signed Bundle / APK klicken, Android App Bundle wählen, Release-Keystore auswählen, Passwort eingeben und Build starten.
5. Google Play Console Release: Unter Release > Produktion (oder Geschlossener Test) eine neue Version erstellen und die erzeugte .aab-Datei hochladen.

Datenbank-Tabellen, Auth & Kopierschutz

Alle Benutzerkonten, Käufe und Admin-Rollen liegen in Supabase. Die Daten sind strikt normalisiert und gegen unbefugten Zugriff geschützt:

1. Die 3 Kern-Tabellen in Supabase (PostgreSQL)

Tabelle: produkte

Katalog aller Hörbücher & Meditationen.
• id: Primärschlüssel (z. B. mensch_sein)
• titel, beschreibung
• audio_path: Cloudflare R2 Stream URL
• dauer: Sekunden (z. B. 3519)
• play_store_id: ID für Google Play

Tabelle: kaeufe

Verknüpft Nutzer mit freigeschalteten Inhalten.
• user_id: Supabase Auth UUID
• produkt_id: Entspricht produkte.id
• status: 'completed'
• created_at: Kaufzeitstempel

Tabelle: profiles

Benutzerkonten & Berechtigungen.
• id: UUID des Nutzers
• email: Normalisierte Mailadresse
• rolle: 'admin' oder 'user'
• is_premium: Abo-Freischaltung

2. Datenfluss bei Kauf & Freischaltung

Kanal Ablauf der Transaktion Wo wird der Kauf gespeichert?
Webseite
(Stripe / PayPal)		 Kunde wählt Produkt -> Checkout via Zahlungsdienstleister -> Bei Erfolg Rückleitung zur App. Eintrag in Supabase Tabelle kaeufe verknüpft mit der user_id. Zudem im lokalen Offline-Manager für Schnellzugriff.
Android App
(Google Play)		 Kauf über natives Google Play Dialogfenster mit hinterlegtem Google Pay / Guthaben. Google Play Billing liefert den Kauf-Token. Die App trägt den Datensatz in Supabase kaeufe ein und spiegelt ihn in den internen App-Speicher.

3. Intelligente Schutz- & Komfortmechanismen

E-Mail Alias-Gleichbehandlung (@googlemail vs @gmail)

Das System normalisiert im Frontend automatisch: @googlemail.com und @gmail.com werden für dieselbe Person als identisch behandelt. Käufe, Hörpositionen und Admin-Status gehen auch bei Google-SSO-Login-Wechsel nie verloren.

Flugmodus & geschützter Offline-Speicher

Hörbücher werden bei Offline-Speicherung in den isolierten App-Cache (IndexedDB / Capacitor Sandbox) geladen. Es existiert keine ungeschützte MP3 im Dateisystem. Der Player merkt sich die Abspielsekunde alle 2 Sekunden im localStorage für nahtloses Fortsetzen.

4. Schnelle Hilfe bei typischen Support-Fällen

Symptom Häufigste Ursache Lösung
Admin-Status weg nach Login Login mit neuer E-Mail oder neuem SSO-Alias. In Supabase Tabelle profiles Spalte rolle auf admin setzen. (Self-Healing im Frontend ist ebenfalls aktiv).
Neues Buch im Store nicht kaufbar Google Play ID weicht von Supabase play_store_id ab. Prüfen, ob in der Google Play Console das Produkt mit exakt der gleichen ID aktiv geschaltet ist.

Sicherheits-Roadmap: Absicherung vor Skalierung

Strategische Vormerkung: Aktuell läuft die Plattform in einer überschaubaren Nutzerphase stabil. Sobald die Nutzerzahlen steigen, müssen folgende 4 Sicherheits- und Härtungsmaßnahmen umgesetzt werden, um das System gegen Angriffe und Datenlecks abzusichern:

1. GitHub -> Hostinger Webhook-Absicherung Priorität: Hoch

Risiko: Der Webhook-Endpunkt auf Hostinger, der bei jedem Git-Push automatisch die Webseite neu zieht, könnte ohne Geheimschlüssel von unbefugten Dritten getriggert oder manipuliert werden.
Härtungsmaßnahme:
• In den Hostinger Git-Einstellungen ein geheimes Webhook Secret hinterlegen.
• In GitHub unter Settings > Webhooks dasselbe Secret eintragen, sodass Hostinger die HMAC-Signatur jedes Pushes kryptografisch validiert.
• Zugriff auf die Webhook-URL auf GitHub IP-Ranges beschränken.

2. Hostinger Server-Härtung & Verzeichnisschutz (.htaccess) Priorität: Hoch

Risiko: Wenn beim Git-Pull versehentlich ein .git-Ordner oder Konfigurationsdateien im public_html landen, könnten Angreifer die gesamte Historie herunterladen.
Härtungsmaßnahme:
• In der .htaccess-Datei von Hostinger den direkten Zugriff auf sensible Pfade sperren:
RedirectMatch 404 /\.(git|env|config)
• Verzeichnis-Listing (Directory Browsing) per Options -Indexes global abschalten.
• HTTP-Sicherheits-Header setzen: X-Frame-Options: SAMEORIGIN, X-Content-Type-Options: nosniff.

3. Supabase Row Level Security (RLS) & Key-Trennung Priorität: Kritisch

Risiko: Im Frontend-Code ist der Supabase Anon-Key sichtbar. Ohne strikte RLS-Regeln könnte ein versierter Nutzer fremde Kaufhistorien oder E-Mails auslesen.
Härtungsmaßnahme:
• RLS auf allen Tabellen aktivieren: Tabelle kaeufe darf nur Zeilen liefern, bei denen auth.uid() = user_id ist.
• Tabelle profiles darf für normale Nutzer nur das eigene Profil lesbar und bearbeitbar machen.
• Niemals den Service-Role-Key im Code verwenden – dieser verbleibt ausschließlich in geschützten Edge-Functions.

4. Android Keystore-Sicherung & Signaturschutz Priorität: Mittel

Risiko: Geht die Android Keystore-Datei verloren oder wird kompromittiert, können keine App-Updates mehr im Google Play Store eingereicht werden.
Härtungsmaßnahme:
• Keystore-Datei (.jks) und Passwörter stehen in .gitignore und dürfen niemals auf GitHub hochgeladen werden.
• Verschlüsseltes Offline-Backup des Keystores anlegen (z. B. auf sicherem USB-Stick & Passwortmanager).
• Google Play App Signing (Play Feature) nutzen, damit Google die App mit dem Master-Key signiert.

📌 Zusammenfassung für den nächsten Entwicklungsschritt: Dieses Dokument ist im Git-Repository gesichert. Wenn das Marketing anläuft und die Nutzerbasis wächst, wird diese Seite 4 Schritt für Schritt als Sicherheits-Sprint abgearbeitet, um Hostinger, GitHub und Supabase abzusichern.
